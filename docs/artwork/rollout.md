## Rollback

- D1: run rollback-catalog.sql only for this catalog's exact IDs and version. It deactivates/revokes new cards while retaining records, rights evidence and history. It excludes the existing Tintoretto and every prior person/place record. Source-policy triggers invalidate caches. Verify the new active count is zero and old rows still match the baseline. Do not delete rows or rerun an older migration.
- Worker: restore the recorded prior deployment (current baseline e7bfeb16-768c-43b6-bc52-305926f590a3), preserving settings/bindings. Verify module bytes and a public reading response. Deactivate cards before Worker rollback so clients receive no unsupported additions.
- Client/feed: preserve the new release as historical; restore the exact prior canonical feed bytes using staged uploads and renames, keeping both assets. Do not overwrite old IPA or tag contents. A source/IPA rollback cannot force already installed clients to downgrade; they continue to handle the older public API safely.
- A later retry after a deliberate catalog revocation requires a fresh reviewed forward migration or explicit plain UPDATE of the exact verified rows/version. Do not use the initial seed's UPSERT to change an already registered rights state; SQLite trigger conflict behavior differs from a plain UPDATE.
